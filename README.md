# AIRules

> 策划 / 程序通用的 AI 协作全局规则（Cursor / Claude / DSH）

一套面向游戏开发的 AI 协作规范：**业务代码、策划案、配表三类改动，必须先出方案、得到明确确认，再动手；其他方向只给提议，等审阅、补充、拍板。**

它约束的不是“AI 能不能做”，而是“AI 在什么条件下才允许动手、动手时改多少、改完怎么证明”。

## 为什么需要它

AI 协作里最常见的三类事故：

1. **不问就改**：自己挑一个解释就开始改代码/文档/表，改完才发现方向错了。
2. **改过头**：只让改 A，顺手重构了 B、调了格式、删了“看起来没用”的代码，diff 里一半是无关改动。
3. **说做了但没验证**：没跑测试、没导表、没对照验收标准，却说“已完成”“应该没问题”，甚至编造 API/字段/数值。

AIRules 用三件事解决：

- **三类门禁**：业务代码、策划案、配表，未确认不动手。
- **三档边界**：Always / Ask / Never，把“能做、要问、绝不能做”分清。
- **方案—确认—验证闭环**：先方案、再确认、按方案实施、每步 verify、最后 Handoff。

## 核心规则速览

| 维度 | 规则 |
|---|---|
| 受控对象 | 业务代码、策划案、配表；判定看“行为 / 规则 / 数值 / 体验 / 验收是否会变” |
| 拿不准 | 按受控处理，先问；不自行豁免 |
| 未确认时 | 只读调研、写方案、给提议；不改受控文件 |
| 方案 | 10 段模板；至少范围/影响/验证/回滚/待确认；步骤写“动作 → verify” |
| 确认 | 明确确认词；有决策点必须选；只覆盖方案范围；超范围失效 |
| 实施 | 每条改动对应方案条目；每步验 postcondition；不顺手重构 |
| 其他方向 | 只给提议（现状/目标/2–3 方案/成本收益/推荐），不改文件 |
| 诚实与验证 | 不编造；不假验证；评审列 3 个失败模式；重构列不变量 |
| 策划/配表 | GDD 8 段；配表写旧值→新值、关联表、导表校验、回滚 |
| 程序 | Unity 架构 7 条 + 最小改动 + 诚实验证 |
| 交付 | 固定 Handoff：改动/文件/验证/风险/下一步；项目要有命令表 |

## 快速开始

### Cursor

1. 在项目根新建 `.cursor/rules/global-rules.mdc`（或 `~/.cursor/rules/global-rules.mdc`）。
2. 文件头加 frontmatter：

```yaml
---
description: 策划/程序通用 AI 协作全局规则：业务代码、策划案、配表三类改动先方案后确认
alwaysApply: true
---
```

3. 粘贴 [GLOBAL-RULES.md](GLOBAL-RULES.md) 正文。
4. 在 `Customize → Rules` 确认已加载；如果工程不在用户主目录下，优先用项目内规则。

### Claude

1. 推荐新建 `~/.claude/rules/global-rules.md`，粘贴 [GLOBAL-RULES.md](GLOBAL-RULES.md) 正文；也可以合并进 `~/.claude/CLAUDE.md`。
2. 用 `.md`，不要用 `.mdc`；全局规则不需要 `paths`。
3. 用 `/context` 检查是否加载。

### DSH

1. 把 [GLOBAL-RULES.md](GLOBAL-RULES.md) 正文写入 `~/.dsh/AGENTS.md`（新建）。
2. 或在项目根放 `AGENTS.md` / `CLAUDE.md`。
3. 不要放 `~/.dsh/rules/`，DSH 内置加载器不读该目录。

## 适用对象

- 使用 Cursor / Claude / DSH 进行游戏开发的策划、程序、TA、测试。
- 需要“先对齐再动手”的团队，或经常被 AI 的“顺手改动”“假验证”困扰的个人开发者。
- 希望把 AI 协作规范沉淀成可复用、可审查、可交接文档的团队。
